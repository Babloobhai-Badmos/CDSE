# Blog, audio and storage setup (Supabase + Cloudflare R2)

The code for this is already in the repo. This guide covers the steps that need
your own accounts. Until they're done, the site keeps working from the built-in
list of 16 posts (see `js/posts.js`).

> **Status:** `js/config.js` is filled in and the project answers with a valid
> publishable key, but the schema has **not** been created — `public.posts` does
> not exist, so the site still uses its built-in post list. Start at step 1.
> `supabase/functions/upload-file/` must also be deployed, or the editor's
> **Upload audio** / **Upload file** buttons will fail.

## What lives where

| Thing | Where |
|---|---|
| Post text, authors, publish state, audio link | Supabase database (`posts` table) |
| Editor logins | Supabase Auth + `editors` table |
| MP3 audio files, images, PDFs | Cloudflare R2 bucket |
| Text-to-speech | **Outside the site** — you make the MP3, then upload it |
| Uploading | Supabase Edge Function `upload-file` |

Audio is **not** generated by this site. You produce the MP3 with whatever TTS
tool or human reader you prefer, then upload it through `admin.html`. That keeps
the site free of TTS credentials and avoids the Edge Function time limits that
long posts would hit. See "Publish a post with audio" below.

## 1. Supabase

1. Create a project. In **SQL Editor**, run these in order:
   - `supabase/migrations/20260101000000_blog.sql` — `editors` + `posts` tables, RLS policies
   - `supabase/migrations/20260102000000_post_images.sql` — adds `image_url` / `image_alt`
   - `supabase/migrations/20260103000000_grants.sql` — table privileges for the API roles
   - `supabase/seed.sql` — adds the 16 archive posts as links to nlujcdse.in

   **Don't skip the grants file.** Row-level security filters rows; it does not
   give a role permission to read the table at all. Without the grants the API
   answers every query with `42501 permission denied for table posts`, and the
   site quietly falls back to its built-in 16-post list — which looks exactly
   like "my new post never appears".
2. **Authentication → Providers → Email**: keep email sign-in on, and turn **off** "Allow new users to sign up". Create each editor yourself under **Authentication → Users → Add user**.
3. Make that user an editor (SQL Editor):
   ```sql
   insert into public.editors (user_id)
   select id from auth.users where email = 'editor@example.org';
   ```
4. Copy **Project URL** and the **anon / publishable** key (Project Settings → API) into `js/config.js`. These two are safe to publish. Never put the `service_role` key in the site.

Free projects pause after about a week without activity. Open the site or the
dashboard regularly, or add a scheduled ping, so the blog doesn't go offline.

## 2. Cloudflare R2

1. Bucket → **Settings → Public access**: connect a custom domain. Currently `https://cdse.taskboard.co.in`. The `r2.dev` address is fine for testing only. Upload one test file and open `https://<domain>/<key>` — if it downloads, the domain is live.
2. **R2 → Manage API tokens**: create a token with *Object Read & Write* limited to this bucket. Note the Access Key ID, Secret, and your Account ID.

The bucket is never indexed or browsable: a request for a key that does not
exist returns a Cloudflare 404, and `/` returns 404 too. That is expected.

You never need to open the Cloudflare dashboard again after this — uploads go
through the editor.

## 3. Deploy the function

`upload-file` is **code that runs on Supabase's servers**, not on your computer
and not in the browser. It needs your R2 credentials to write to the bucket, and
those credentials must never be in `js/` (anyone can read that). So they are set
as *secrets* on the Supabase side, then the function is uploaded once:

```bash
supabase login
supabase link --project-ref <your-project-ref>
supabase secrets set \
  R2_ACCOUNT_ID=... R2_ACCESS_KEY_ID=... R2_SECRET_ACCESS_KEY=... R2_BUCKET=... \
  R2_PUBLIC_BASE_URL=https://cdse.taskboard.co.in
supabase functions deploy upload-file
```

What that actually does:

| Piece | Where it lives |
|---|---|
| `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `R2_BUCKET` | Supabase secret store, readable only by the function |
| `R2_PUBLIC_BASE_URL` | Same — the bucket's public base URL, used to build links for audio, images and PDFs alike |
| `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY` | Injected automatically; don't set these |
| The function code | Supabase Edge Functions runtime |

`R2_PUBLIC_BASE_URL` is **one** value for the whole bucket — the files are
separated by key prefix (`audio/`, `images/`, `uploads/`), not by domain. The
older name `AUDIO_BASE_URL` still works, but new setups should use
`R2_PUBLIC_BASE_URL`.

Pick that hostname deliberately: the full URLs are saved into `image_url` and
`audio_url` when a post is saved, so changing it later does **not** rewrite rows
in `public.posts`. Moving to `media.cdsenluj.in` afterwards means either
re-uploading or a `replace(...)` across the table.

Without this step the **Upload audio** / **Upload image** / **Upload file**
buttons return "Failed to fetch" or 404, because the endpoint does not exist yet.

**No CLI?** You can do the same in the dashboard: **Edge Functions → Deploy a
new function**, name it `upload-file`, paste
`supabase/functions/upload-file/index.ts`, then add each secret under
**Edge Functions → Secrets**. Deploy. Same result; the CLI is just repeatable.

> It has **not been run end to end against a real bucket yet**. Upload one short
> MP3 first and confirm it plays before relying on it.

## 4. Publish a post with audio

1. `admin.html` → sign in → pick or create the post.
2. Fill in title, slug (auto-filled from the title), author, and the post text.
   Blank line between paragraphs; start a line with `## ` for a heading.
3. **Cover image** (optional): under **Upload cover image to R2**, choose a
   jpg/png/webp and press **Upload image**. The URL fills in, and the
   description field auto-fills with the title if you leave it blank. That
   description is the image's alt text — edit it if the picture says something
   the title doesn't. The same image is used on the post page and its listing
   card.
4. Under **Upload audio to R2**, choose your `.mp3` and press **Upload audio**.
   It goes to `audio/<slug>.mp3` and the **Audio file URL** box fills in.
5. Tick **Published** and press **Save post**. That stores the links and the
   measured audio duration in Supabase and marks `audio_status = ready`.

Practical notes:

- **Keep it MP3.** The upload proxy stores the file as-is and serves it as
  `audio/mpeg`. AAC/m4a will upload but some browsers won't play them.
- **Use 64–96 kbps mono for speech.** A 3000-word post is roughly 20 minutes;
  at 128 kbps stereo that's already ~19MB, close to the 25MB cap. At 64 kbps
  mono the same post is about 9MB.
- **Duration is measured in the browser** at upload time, so the player shows the
  right length immediately instead of `–:––`.
- **Re-uploading the same slug replaces the file** at the same R2 key, and the
  `?v=` suffix changes so browsers fetch the new one.
- **Editing the text later** prompts you to keep or drop the existing audio
  rather than silently unlinking it.
- **No audio yet?** The post page falls back to the device's own read-aloud voice.

## How audio is presented

- Posts with an MP3 get an accessible player: play/pause, back 15s, forward 30s, speed 0.75x–2x, seek bar, remembers your place, lock-screen controls on phones, and a download link. Nothing autoplays.
- Posts without an MP3 but with text offer the browser's built-in read-aloud as a fallback.
- Listings show a small "Audio" label on posts that have an MP3.
- If you publish AI-generated audio, say so on the page or in the About text.

## How the post page loads

- `js/posts.js` fetches only the columns the post page needs (not `select=*`).
- The result is cached in `sessionStorage` for 5 minutes, so back/forward and
  repeat visits render without a network round trip.
- Listing pages warm that cache when a title is hovered or focused, so clicking
  through usually feels instant.
- Long posts with 3+ headings get a contents list with anchor links; every post
  gets a reading-progress bar (decorative, hidden from screen readers).
